# Задание 5. Проектирование GraphQL API для client-info

## Анализ существующего контракта 

В контракте три эндпоинта, все — чтение, все — по идентификатору клиента:

| REST-операция | Что возвращает | Модель |
|---|---|---|
| `GET /v1/clients/{id}` | карточку клиента | `Client`: `id`, `name`, `age` |
| `GET /v1/clients/{id}/documents` | список документов клиента | `Document`: `id`, `type`, `number`, `issueDate`, `expiryDate` |
| `GET /v1/clients/{id}/relatives` | список родственников клиента | `Relative`: `id`, `relationType`, `name`, `age` |

Ключевые наблюдения:

1. Все три ресурса сгруппированы вокруг одного сущностного центра — клиента. Это естественная «звезда», а не независимые сущности: документы и родственники не имеют смысла вне идентификатора клиента.
2. Все операции — GET по ID, то есть классическое «поедание» данных по одной сущности, и в GraphQL это одна точка входа `client(id)` с произвольным набором под-полей.
3. В самом контракте модели упрощены, но в условии задачи сказано, что контактов тоже хватает на отдельный объект данных. Их нет ни в модели `Client`, ни в эндпоинте — значит, в реальном API они живут на отдельном ресурсе (как-то в духе `/clients/{id}/contacts`), и в GraphQL им положено своё место.

## Решения по схеме

Файл схемы: `schema.graphqls`.

### 1. Одна точка входа вместо трёх эндпоинтов

`type Query` содержит единственный запрос `client(id: ID!)`. Все операции REST закрываются им же, различается только набор запрашиваемых под-полей:

```graphql
# эквивалент GET /v1/clients/{id}
{ client(id: "c-1001") { id name age } }

# эквивалент GET /v1/clients/{id}/documents
{ client(id: "c-1001") { id documents { id type number issueDate expiryDate } } }

# эквивалент GET /v1/clients/{id}/relatives
{ client(id: "c-1001") { id relatives { id relationType name age } } }
```

### 2. Под-объекты — поля типа Client, а не отдельные query

Документы, родственники и контакты объявлены как поля `documents`, `relatives`, `contacts` типа `Client`, а не как отдельные методы `Query`. Это отражает реальную структуру данных (они принадлежат клиенту), даёт IDE автодополнение прямо внутри карточки и позволяет комбинировать объекты в одном запросе:

```graphql
# сценарий «оформление полиса»: имя + действующий паспорт + родственники-выгодоприобретатели
# — один HTTP-запрос вместо трёх
{ client(id: "c-1001") {
    name
    documents { type number expiryDate }
    relatives { relationType name age }
} }
```

Именно это убирает проблему кратного роста RPS: потребителю нужен один сетевой вызов, а не цепочка.



## Примеры запросов для типовых сценариев

**Личный кабинет, шапка профиля** (минимум данных):

```graphql
{ client(id: "c-1001") { name age } }
```

**Оформление страховки** (нужны документы и родственники-выгодоприобретатели):

```graphql
{ client(id: "c-1001") {
    name
    documents { id type number issueDate expiryDate }
    relatives { id relationType name age }
} }
```

**Сценарий с условием** — стандартные директивы `@include`/`@skip` позволяют менять состав данных переменной, не пересобирая запрос:

```graphql
query GetClient($withRelatives: Boolean!) {
  client(id: "c-1001") {
    name
    relatives @include(if: $withRelatives) { relationType name age }
  }
}
```
